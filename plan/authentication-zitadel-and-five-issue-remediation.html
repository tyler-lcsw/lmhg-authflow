Authorization Manager authentication and five-issue remediation plan

Plan-only artifact for aligning the legacy Auth Forms service with the staff dashboard and ZITADEL, while resolving the five commit blockers identified in the current worktree.

Prepared 2026-08-09 Plan only PHI-safe verification Username + password initial goal

Outcome

Staff authenticate with an administratively created ZITADEL local account using a username and password. The dashboard completes Authorization Code flow with PKCE, stores the resulting application session only in secure HttpOnly cookies, enforces the least-privilege authorization_operator role and ePHI confirmation, and proxies Authorization Manager requests. The browser receives neither ZITADEL tokens nor the Authorization Manager service token.

Authorization Manager remains defense-in-depth protected: production requires a service token and a private network path; tokenless development is an explicit loopback-only mode. This preserves ZITADEL as the user-authentication authority without treating the legacy service as publicly trusted merely because integration is underway.

Initial ZITADEL policy target

  • Keep OIDC Authorization Code + PKCE; “username and password only” describes the hosted user-authentication method, not the OAuth grant type.
  • Use each staff member's email address as the ZITADEL login username.
  • Enable Username Password allowed.
  • Disable public self-registration.
  • Disable external identity-provider login and account creation for this initial phase.
  • Disable passkeys/passwordless and do not request passkey registration.
  • Disable Force MFA and Force MFA for local authenticated users; set MFA-init prompting so users are not asked to enroll during the initial phase.
  • Create users administratively, set an initial password, and require password change on first login with the ZITADEL v2 field human.password.changeRequired=true.
  • Disable self-service password reset; password resets are administrator-only during this phase.
  • Use authorization_operator for Authorization Manager access while preserving the existing ePHI confirmation gate; do not grant developer merely for this workflow.
  • Define a lockout threshold and password-complexity policy before inviting staging users; “password only” must not mean “no brute-force protection.”
  • Before mutation, export the effective inherited policy and record exact rollback operations, policy scope, administrator owner, and behavior for users who already have MFA or passkey factors.

Task 2 — Define and harden the dashboard session and proxy contract

Description: Make the dashboard the explicit identity-propagation boundary instead of assuming PKCE alone proves a secure session or trusted audit actor.

Acceptance criteria:

  • The browser cookie contains only an opaque session identifier. ZITADEL credentials and current role state remain in protected server-side storage with signing/encryption key rotation, fixation prevention, idle and absolute expiry, role refresh/revocation behavior, CSRF protection for state changes, and logout invalidation.
  • The callback consumes one-time state, authorization code, PKCE verifier, and nonce, then validates a pinned signing algorithm/JWKS key, exact issuer, audience and azp rules, nonce, expiry, issued-at/not-before, and required claims. Missing, duplicate, replayed, substituted, or wrongly issued values fail closed.
  • Every /api/legacy/auth-manager/* request verifies the active session, current authorization.manage permission, and a server-side ePHI confirmation bound to the subject, session, Authorization Manager module, and a short expiry. Missing, expired, forged, logout-invalidated, or role-change-invalidated confirmation is denied.
  • The proxy strips browser-supplied x-auth-token, Authorization, and actor headers; forbids redirects and non-allowlisted upstream paths; and redacts tokens from logs/errors. It injects the legacy token plus x-lmhg-actor-assertion: an asymmetrically signed JWT containing issuer dashboard.lmhg.app, audience authorization-manager, subject, session ID, current roles, HTTP method, canonical raw path/query, hash of the exact post-transformation forwarded bytes, iat, an exp no more than 60 seconds later, and unique jti. A shared specification rejects ambiguous/double encodings, pins the signing algorithm, trusts only an approved kid keyring with rotation overlap, and atomically retains replay entries through expiry plus allowed clock skew.

Verification: Dashboard tests cover opaque-cookie/server-token storage; callback signature/algorithm/issuer/audience/azp/nonce/time/required-claim validation and one-time state/code/verifier use; key rotation; idle/absolute expiry; role refresh/revocation; CSRF; hostile headers; redirects; path allowlisting; log redaction; denial without authorization.manage; and missing/expired/forged ePHI confirmation. Authorization Manager validates the actor assertion only after the legacy token, including signature/kid, issuer, audience, time, canonical method/path/query/body hash, atomic one-time jti, clock skew, rotation overlap, and ambiguous-encoding rejection; tokenless local mode rejects actor headers and records local-loopback-unattributed. Browser login/logout smoke proves no ZITADEL or legacy tokens appear in web storage or cookies.

Dependencies: Task 1. System: Dell dashboard source/runtime. Scope: Medium.

Task 3 — Make Authorization Manager fail closed and converge the network path

Description: Replace implicit missing-token bypass with an explicit loopback-only development mode, require the token in production, and remove the now-unneeded Tailscale host publication after confirming the dashboard upstream.

Acceptance criteria:

  • Configuration matrix is explicit: local development permits no token only with AUTH_FORMS_ALLOW_TOKENLESS_LOOPBACK=1 and HOST=127.0.0.1/::1; tests alone may use a test bypass; production/container mode requires a readable token even when Node listens on 0.0.0.0 internally.
  • Missing production token fails startup safely; loopback detection covers IPv4, IPv6, and IPv4-mapped IPv6; wrong or missing tokens return 401 in configured mode.
  • Because dashboard and service are co-located on Dell, Docker publishes Authorization Manager only at 127.0.0.1:3100; direct Tailscale access is unavailable and the dashboard upstream uses loopback.

Verification: TDD for the full startup/bind/auth matrix, runtime listener checks on host and inside container, dashboard connector test, non-loopback denial, and firewall/port metadata. Do not bind the containerized Node process itself to container loopback.

Dependencies: Tasks 1 and 2. Likely files: server.js, auth test helper/integration tests, deploy/dell/compose.yaml, dashboard environment configuration, firewall runbook. Scope: Medium.

Approved implementation decisions

  1. Email address is the login username.
  2. Password resets are administrator-only.
  3. Deletion uses branch A: a minimal audit event plus operational deletion. The implementation retains only the identifiers and security metadata required to prove the deletion event, never the authorization payload or PDF path.
